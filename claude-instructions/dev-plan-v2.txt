2. Архитектура проекта — Feature-Sliced Design (FSD)
Вся кодовая база строго следует FSD. Нарушение правил импортов и слоёв недопустимо. Каждый разработчик обязан изучить https://feature-sliced.design перед началом работы.

2.2 Правила FSD — обязательны к соблюдению
Импорты только вниз по слоям: app → pages → widgets → features → entities → shared. Запрещено импортировать из вышестоящего слоя.
Каждый слайс содержит: index.ts (публичный API экспорт), ui/ (компоненты), model/ (хуки, стор), api/ (запросы), lib/ (хелперы), types/ (типы).
Компонент = JSX + пропсы/хуки. Вся логика — в хуках (model/) или сервисах (api/). В теле компонента нет прямых fetch, сложных условий, работы с БД.
shared/ui — только "глупые" компоненты. Без зависимостей от entities, features, widgets.
Состояние (Zustand stores) живёт в model/ каждого слайса или в features/ если оно сквозное.
CSS Modules подключаются внутри компонента: styles.module.css рядом с компонентом.
Admin-роуты — отдельный App Router segment: src/app/(admin)/

3. Страницы сайта и их содержимое
Все страницы, блоки и поведение описаны по ТЗ и карте сайта. LLM-агент или разработчик должен реализовать каждый пункт точно.

Берётся из SiteSettings через getStaticProps / ISR

⚑  Блоки расположены строго в указанном порядке сверху вниз.
Блок 1: Hero-слайдер
Полноэкранный (100vh или фиксированная высота) слайдер на Swiper.js
Каждый слайд: фоновое изображение + overlay, заголовок H1, подзаголовок, кнопка CTA

Автоплей с паузой при hover

Изображения через next/image с priority на первом слайде
Блок 2: Актуальные предложения
Заголовок раздела: "Актуальные предложения"

Карточка (RoomCard widget): фото (next/image lazy), площадь, этаж, цена/мес, статус-бейдж, кнопка "Оставить заявку"
Кнопка "Смотреть все офисы" → /offices
Блок 3: Почему арендаторы выбирают нас
Заголовок: "Почему арендаторы выбирают нас?"
8 карточек-преимуществ: иконка (SVG) + заголовок + краткий текст
Данные из таблицы Advantage в БД, управляются из админки
Сетка: 4 в ряд на десктопе, 2 на планшете, 1–2 на мобильном
Блок 4: Наши арендаторы
Заголовок: "Наши арендаторы"
Логотипы компаний-арендаторов (горизонтальная прокрутка или сетка)
Данные из таблицы Tenant, управляются из админки (drag & drop сортировка)
Изображения с next/image, aspect-ratio сохранён
Блок 5: Форма обратной связи
Заголовок: "Свяжитесь с нами"
Поля: Имя (обязательно), Телефон (обязательно), Email (опционально), Сообщение (опционально)
Чекбокс согласия с Политикой персональных данных — обязательный

Карта Яндекс.Карт или 2GIS (выбор при разработке, настраивается через SiteSettings)

3.3 Каталог помещений /offices
Фильтры (features/room-filter)
Фильтр по статусу: все / свободно / бронь / сдано
Фильтр по площади: от / до (числовой input)
Фильтр по этажу: выпадающий список или чекбоксы
Фильтр по цене: от / до
Сортировка: по цене (возр/убыв), по площади, по этажу
Состояние фильтров — в Zustand store (features/room-filter/model/)
URL-параметры синхронизируются с фильтрами (useSearchParams) для копирования ссылки
Сброс фильтров — кнопка "Сбросить"
Сетка карточек
RoomCard (widget): фото (lazy next/image), площадь, этаж, цена/мес, бейдж статуса, CTA-кнопка
CTA по статусу: free → "Оставить заявку", reserved → "Раннее бронирование", rented → "Уточнить наличие"
Пагинация внизу: по 9 или 12 карточек на страницу
При изменении фильтров — плавный scroll to top сетки
Skeleton-лоадер пока данные загружаются
3.4 Карточка помещения /offices/[slug]
Хлебные крошки: Главная → Аренда офисов → [название]
Галерея фотографий: главное фото крупно + миниатюры ряд снизу (Swiper). Клик на миниатюру — сменить главное. Клик на главное — lightbox (features/gallery-lightbox)
Таблица характеристик — показывать ТОЛЬКО заполненные поля:
Номер помещения, Тип помещения, Площадь (м²), Этаж
Планировка, Наличие воды, Санузел, Окна
Вход (описание), Тип аренды, Интернет, Минимальный срок аренды
Блок цены: крупно цена/мес + кнопка "Оставить заявку" (открывает форму с предзаполненным номером помещения)
Описание помещения (richtext из БД, рендер безопасного HTML)
"Подходит для": список тегов/иконок из поля suitableFor[]
ISR: revalidate каждые 60 секунд
SEO: title = "[название] — аренда, [площадь] м²", description из первых 160 символов описания, OG-image

Карточка услуги /services/[slug]
Заголовок услуги

Кнопка "Оставить заявку" → открывает LeadForm с предзаполненной темой (название услуги)

3.6 Фотогалерея /gallery

6. Административная панель
6.1 Скрытость и защита
⚑  Ни один публичный файл, HTML, JS-бандл, robots.txt, sitemap.xml не должен содержать упоминания admin-пути. Это строгое требование.
Уровень защиты
Реализация
Secret slug
Роут: /[adminSlug]/... где adminSlug = значение переменной окружения ADMIN_SLUG. Пример: ADMIN_SLUG=xK9mQr2p. Нигде не захардкожен в коде. Читается только через process.env.ADMIN_SLUG.
Middleware
src/app/middleware.ts проверяет каждый запрос к (admin) сегменту: 1) pathname начинается с /[ADMIN_SLUG], 2) есть валидная сессия NextAuth. Если любое условие не выполнено — возвращает 404 (не 401, не 403, именно 404).
NextAuth
Credentials provider: email + пароль (bcryptjs). JWT-сессия. httpOnly + secure cookie. Бот-защита: после 5 неверных попыток — блокировка IP на 15 мин (in-memory Map или Redis).
Robots / Sitemap
robots.txt: User-agent: * / Disallow: /[ADMIN_SLUG]/. Sitemap.xml не содержит admin-url. В middleware для всех (admin) запросов добавляется заголовок X-Robots-Tag: noindex, nofollow.
JS-бандл
Все admin-компоненты — dynamic import с ssr: false. В публичном бандле нет кода и строк admin-роутов. ADMIN_SLUG читается только на сервере (не попадает в NEXT_PUBLIC_).
Nginx
Опциональный доп. слой: location /[ADMIN_SLUG] требует заголовка X-Admin-Request: true. Без него — 444 (drop). Устанавливается в docker-compose через proxy_set_header.

10. Формы, валидация и безопасность
10.1 Форма заявки (LeadForm)
Поля: name (обязательно, мин. 2 символа), phone (обязательно, маска +7 или RU формат), email (опционально, валидный email), message (опционально, макс. 1000 символов)
Чекбокс согласия с Политикой ПДн — обязателен, без него кнопка неактивна
Honeypot: скрытое поле <input name="website" tabIndex={-1} autoComplete="off"> — если заполнено, API возвращает 200 но не сохраняет
Клиентская валидация: React Hook Form + Zod. Ошибки появляются при blur или submit.
Серверная валидация: API Route /api/leads повторно валидирует через Zod
Rate limit: максимум 5 заявок с одного IP за 15 минут. Превышение → 429 с сообщением пользователю
Optimistic UI: кнопка "Отправляется..." при pending, "Готово!" при успехе
При ошибке сервера — понятное сообщение пользователю, не технический текст
После успеха форма очищается, Modal закрывается через 2 секунды
10.2 Общая безопасность
Все API Routes с мутациями (POST/PUT/DELETE) для (admin) — проверяют сессию NextAuth
CSRF: Next.js App Router использует SameSite cookies, дополнительно CSRF-токен для форм
XSS: richtext из БД рендерится через dangerouslySetInnerHTML ТОЛЬКО после санитизации (sanitize-html или DOMPurify на сервере)
SQL Injection: Prisma использует параметризованные запросы, прямой SQL не используется
Env переменные: ADMIN_SLUG, DATABASE_URL, NEXTAUTH_SECRET, EMAIL_* — только в .env, не в NEXT_PUBLIC_
Заголовки безопасности в next.config.ts: X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin
Content Security Policy: настраивается в next.config.ts с учётом карты и загрузки изображений
